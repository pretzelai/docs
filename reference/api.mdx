Cord exposes a REST API for programmatic access. Use it to start sessions from scripts, CI pipelines, or your own tools.

## Authentication

The API uses **Cord API keys** for authentication. Create a key in **Settings > Cord API**.

Each key can be scoped to:
- **All repositories** in your organization
- **Selected repositories** only

Include your key in the `Authorization` header:

```bash
curl -H "Authorization: Bearer cord_sk_..." \
  https://api.runcord.com/api/v1/repositories
```

<Warning>
API keys are shown once at creation and stored as a hash. If you lose a key, create a new one.
</Warning>

## Endpoints

### List repositories

Returns repositories the API key has access to.

```bash
GET /api/v1/repositories
```

**Response:**
```json
[
  "my-org/my-app",
  "my-org/api"
]
```

### Create a session

Start a new coding session with a prompt. The agent begins working immediately in the background.

```bash
POST /api/v1/sessions
```

**Request body:**

```json
{
  "repository": "my-org/my-app",
  "message": "Add a /health endpoint that returns status ok",
  "model": "cord-open-source/kimi-k2.6",
  "thinking": "default"
}
```

| Field | Required | Description |
|---|---|---|
| `repository` | Yes | Repository full name, repo ID, or an unambiguous repository name the API key can access |
| `message` | Yes | The task description for the agent |
| `model` | No | Model to use, either as `provider/model` or an object with `providerID` and `modelID`. Defaults to your configured default. |
| `thinking` | No | Thinking/reasoning variant string. You can also send `variant`. |

**Response:**
```json
{
  "ok": true,
  "sessionId": "session_xyz789",
  "repository": {
    "id": "repo_abc123",
    "name": "my-app",
    "fullName": "my-org/my-app",
    "defaultBranch": "main"
  },
  "agentType": "opencode",
  "model": {
    "providerID": "cord-open-source",
    "modelID": "kimi-k2.6"
  },
  "thinking": "default",
  "status": "queued"
}
```

### Storage attachments

Manage files in your [persistent storage](/core-concepts/persistent-storage):

```bash
GET    /api/v1/storage-attachments
POST   /api/v1/storage-attachments/upload-plan
POST   /api/v1/storage-attachments/upload-file
POST   /api/v1/storage-attachments/finalize-upload
POST   /api/v1/storage-attachments/upload-status
POST   /api/v1/storage-attachments/retry-upload-plan
POST   /api/v1/storage-attachments/report-upload-result
POST   /api/v1/storage-attachments/discard-upload
PATCH  /api/v1/storage-attachments/{id}
DELETE /api/v1/storage-attachments/{id}
```

## Use cases

**CI/CD integration** -- Trigger a Cord session when a specific event happens in your pipeline (e.g., "a flaky test was detected, investigate and fix it").

**Custom automation** -- Create sessions based on external events: monitoring alerts, customer feedback, support tickets.

**Agent-to-agent** -- Have one agent use the Cord API to start another session for a sub-task.

**Scheduled tasks** -- Use a cron job to start sessions for recurring maintenance (dependency updates, code cleanup).

## CLI

The Cord CLI is a separate tool for authentication, provider management, and persistent storage uploads. It supports browser CLI auth and API-key auth via `cord auth login --api-key <key>` or `CORD_API_KEY`. Provider commands require browser CLI auth; Persistent Storage commands can use either browser CLI auth or API-key auth.

See the full [CLI reference](/reference/cli) for installation, all commands, and detailed usage.
