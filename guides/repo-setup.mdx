## Connecting a repository

1. Go to your Cord dashboard
2. Click **Add Repository**
3. Select a repo from your GitHub account or organization
4. Cord runs an AI-powered setup wizard

You can connect repos from any GitHub organization you have access to. Cord needs read/write access to create branches and pull requests.

## AI-powered setup wizard

When you add a repo, Cord's AI setup chat detects your project configuration automatically:

- **Package manager** -- npm, yarn, pnpm, bun
- **Framework** -- Next.js, Vite, Express, Django, Rails, etc.
- **Build commands** -- install, build, dev server start
- **Port** -- which port your dev server runs on
- **Runtime processes** -- any background services your project needs

The wizard proposes a configuration that you can review and adjust. If something looks wrong, you can chat with the AI to refine the setup.

## Root directory

If your repo is a monorepo or your project lives in a subdirectory, set the **root directory** in repository settings. This tells the agent and sandbox where the project actually starts (e.g., `apps/web` or `packages/api`).

## Build commands

Cord detects these automatically, but you can override them:

| Command | Description | Example |
|---|---|---|
| **Install** | Install dependencies | `npm install`, `pnpm install` |
| **Build** | Build the project | `npm run build`, `next build` |
| **Dev** | Start the dev server | `npm run dev`, `next dev` |

For a complete reference of every build setting -- runtime processes, endpoints, Docker Compose, build hooks, and more -- see [Build settings](/guides/build-settings).

## Runtime processes

Some projects need more than just a dev server. In repository settings, you can define multiple **runtime processes** that start with every sandbox:

- A backend API server
- A frontend dev server
- A database or queue (via Docker Compose)
- A watch process for TypeScript compilation

Each process gets a name and a start command. They all run in the sandbox simultaneously.

## Runtime endpoints

Define which URLs should be exposed from the sandbox. Each endpoint maps a port to a preview URL. For example:

- Port 3000 -- frontend dev server
- Port 8080 -- backend API
- Port 5432 -- database (for tools that need direct access)

## Docker and Docker Compose

Docker is available in every sandbox by default. If your project uses Docker Compose for local development (e.g., running Postgres, Redis, or other services), it works the same way in a sandbox.

No additional configuration needed -- just make sure your `docker-compose.yml` is in the repo.

## Build hooks

Build hooks let you run custom scripts at specific points in the sandbox setup:

- **Post-install** -- after dependencies are installed
- **Post-build** -- after the build completes
- **Pre-start** -- before the dev server starts

Use these for things like database migrations, seed scripts, or custom setup steps that aren't covered by the standard build commands.

## Environment variables

Add environment variables in **Repository Settings > Secret Files**:

- Variables are **encrypted at rest** in the database
- **Injected automatically** into every sandbox on startup
- **Write-only** -- after saving, values are hidden in the UI (you can update but not read back)
- Available to the agent and all processes in the sandbox

<Warning>
Environment variables are available to the AI agent running in your sandbox. Don't add secrets you wouldn't want an AI model to see in context.
</Warning>

## Per-repo defaults

Override org-level defaults for a specific repository:

| Setting | Description |
|---|---|
| **Default agent** | Claude Code or OpenCode for sessions on this repo |
| **Default model** | Which provider and model to use |
| **Thinking mode** | Enable/disable extended thinking by default |
| **Branch prefix** | Custom prefix for session branches (default: `cord/`) |

## Sandbox provider

The available sandbox providers are shown in Repository Settings. Your deployment may offer Modal, Daytona, or Freestyle; choose the provider supported for your repo's requirements.

## Build status

View build history and status in repository settings:

- See past builds with timestamps and outcomes
- **Trigger a rebuild** manually if something went stale
- Check build logs for debugging setup issues

<Tip>
If a new session fails to start or has missing dependencies, try triggering a rebuild in repository settings. This refreshes the base image with the latest dependency state.
</Tip>
